# Mod patches

Binary patches applied to third-party mod assemblies, for defects that block a
world from loading and that no configuration switch can avoid. Each patcher
verifies the IL shape it expects and refuses to write anything if the shape has
changed, so a mod update cannot be silently mis-patched.

These are a last resort. Prefer, in order: a config switch, a version pin, an
upstream fix, dropping the mod. Reach for a patch only when the alternative is
losing player data.

## blacksmithing_expanded_null_key.cs

**Mod:** `OdinPlus-BlacksmithingExpanded` 1.1.7
**Defect:** `BlacksmithingItemData.Load()` inserts `item.m_shared` into a static
dictionary with no null check. `m_shared` is null exactly when the game could not
resolve an item's prefab - an item left in a container by a mod that has since
been uninstalled - so `Dictionary.set_Item` throws `ArgumentNullException`.

**Why it matters:** during the one-time Valheim 1.0 world conversion this runs
inside `ZDOMan.ConvertContainers`, so the exception aborts the whole world load:

```
Failed to find item prefab -1482742536
Exception while loading world .../Vangard.db: System.ArgumentNullException
  Parameter name: key
  at BlacksmithingExpanded.BlacksmithingExpanded+BlacksmithingItemData.Load ()
World load failed mid-file. Exiting without save. Check backups!
```

The server then quits and supervisord restarts it, forever. Measured on Vangard
2026-09-13: 451,451 zdos read, abort, ~186-second restart loop, 13 cycles. Both
the Aug 6 and Aug 5 saves failed identically, which is what ruled out disk
corruption - the world was fine, the mod could not read it.

The game itself tolerates a missing prefab; it logs the warning and moves on.
Only this mod turns it into a fatal error.

**Patch:** prepend a null test on the same key and branch past the insert, so an
unresolvable item is not registered. There is nothing to key it by, so skipping
is the only sensible behaviour. 4 instructions added; short branches in the
method are widened because the offsets no longer fit.

**Build and apply:**

```sh
work=$(mktemp -d) && cd "$work"
managed=$VALHEIM_ROOT/<World>/data/bepinex/valheim_server_Data/Managed
core=$VALHEIM_ROOT/<World>/data/bepinex/BepInEx/core
cp "$managed"/*.dll "$core"/*.dll .                     # resolver needs these
cp <profile>/bepinex/plugins/BlacksmithingExpanded/BlacksmithingExpanded.dll bse.dll
mcs -out:fix.exe -r:"$core/Mono.Cecil.dll" blacksmithing_expanded_null_key.cs
MONO_PATH="$core" mono fix.exe bse.dll bse-patched.dll
```

Keep the stock DLL beside the patched one (`.stock-<version>`) so the change is
reversible and visible.

**Scope and lifetime:** `config_merged` is regenerated by `manage_mods.sh deploy`,
so a deploy reverts this. That is acceptable for the migration it was written
for - `ConvertContainers` only runs on a `WorldVersion 37` world, and all five
worlds are now 41. It is still worth reapplying if a world ever loads a
pre-1.0 save again.

**Upstream:** not filed. `OdinPlus-BlacksmithingExpanded` publishes no issue
tracker; its Thunderstore `website_url` is a Discord invite
(https://discord.gg/jkcJCq2sK5), so reporting needs an operator with a Discord
account. Everything needed for that report is in bead `vhp-e0h`.
