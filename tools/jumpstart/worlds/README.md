# Per-world, per-preset jumpstart instantiation

`tools/jumpstart/presets/` says **what a tier is**. This directory says **what
that tier becomes in a particular world**.

```
tools/jumpstart/
  presets/<preset>.yaml            WORLD-AGNOSTIC tier definition  (not owned here)
  jumpstart.py                     driver: keys + RCON grants      (not owned here)
  worlds/
    tier-policy.yaml               WORLD-AGNOSTIC tier -> settings policy
    derive.py                      the generator
    <World>/
      world.yaml                   WORLD-SPECIFIC facts (the only hand-edited file here)
      <preset>/
        settings/
          world-modifiers.env      generated  launch args for this preset
          overrides.yaml           generated  the server-config keys this tier changes
          chest-manifest.yaml      generated  what the kit could not fit in a backpack
        keys.yaml                  generated  the global keys this preset sets
        charactertemplate.yml      generated  the ServerCharacters starting kit
        spawn.yaml                 generated  by `derive.py spawn`: the verified spawn
        blueprints/                BlueprintHunt
        placements.yaml            BlueprintHunt (read here, never written)
```

## The split, and why derivation rather than duplication

Two directories now describe a preset, which is exactly the shape that rots. The
rule is:

* **`presets/<preset>.yaml` is the definition.** Keys, kit, materials, chain
  items, skills, stations. It has no idea which world it will be applied to and
  must never grow a world-specific field.
* **`worlds/<World>/<preset>/` is the instantiation.** Every file in it is
  **generated** by `derive.py` from exactly three inputs — the preset, the
  world-agnostic `tier-policy.yaml`, and the world's `world.yaml`.

Nothing is copied by hand, so the two cannot disagree. Three things enforce it:

1. **`derive.py` imports `jumpstart.py`** and uses its `load_preset` /
   `all_preset_names`. There is one preset parser, not two. A field added to the
   preset schema is visible here immediately.
2. **Every generated file carries a provenance header** naming all three inputs
   and the regenerate command.
3. **`derive.py check <World>` re-derives in memory and diffs**, exiting non-zero
   on any difference. A hand edit to a generated file, or a stale tree after
   someone changes `tier-policy.yaml`, shows up as `DRIFT` rather than as a
   surprise six weeks later. This is the command to wire into CI.
4. **`derive.py check <World>` cross-checks the spawn against `placements.yaml`.**
   The other three rules compare generated files against *this tree's* inputs.
   The spawn is the one value that also depends on a file this tree does not own,
   and that gap is how a character was once dropped in the sea: the solver
   re-solved, the base moved 4.5 km, the template kept the old coordinate and
   nothing noticed. `check` now refuses to render `charactertemplate.yml` at all
   (`HELD`) when `spawn.yaml`'s recorded base no longer matches the current
   `solved` block, when the recorded freeboard is below the floor, when `y` is
   not `ceil(terrain + 1)`, when the point has drifted inside the footprint, or
   when a solved placement has neither a spawn nor a recorded refusal. The
   message names the preset, the spawn, where the base is now and what to run.


Adding a second world is `mkdir worlds/<Name>`, write a `world.yaml`, run
`derive.py build <Name>`. No code changes, and `tier-policy.yaml` is shared, so a
tier means the same thing everywhere.

### Where each fact lives, once

| Fact | Home | Why there |
|---|---|---|
| Kit, materials, skills, stations, keys | `presets/<preset>.yaml` | Tier truth; identical in every world. |
| Which config keys a tier changes, and why | `worlds/tier-policy.yaml` | Tier truth about *settings*; identical in every world. |
| Resource rate, portals, launch preset | `worlds/<World>/world.yaml` `baseline.world_modifiers` | **Single source.** Nine `world-modifiers.env` files read it; changing the fleet's resource rate is one token plus a regenerate. |
| Inventory slots, stack sizes | `worlds/<World>/world.yaml` `inventory` | Comes from that world's deployed profile. |
| Building positions | `<preset>/placements.yaml` | Seed-specific; regenerated by the placement solver after every re-roll. |
| Spawn coordinate, and the terrain proving it is dry | `<preset>/spawn.yaml` | Seed-specific and MEASURED. `derive.py spawn` probes Valheim's generator at 1 m and records the point plus its evidence; `build`/`check` need no terrain, only this file and the current `solved` blocks. The solver's own `spawn_points:` is NOT read — it is an untested offset and it has landed 4.2 m under water. |

### Pinned modifiers

World modifiers resolve as *baseline, overlaid with the preset's non-`Default`
values* — except for the keys in `world.yaml` `baseline.pinned`, which the world
owns outright.

The pin is load-bearing, not decoration. All nine presets still declare
`Resources: More`, written before the fleet settled on `MuchMore`
(`resourcerate 200`, a flat unconditional 2x). Without a pin the merge runs
backwards on exactly the value that is supposed to have one home, and nine tier
files quietly halve the world's drop rate. `Resources` and `Portals` are pinned;
`Combat`, `DeathPenalty` and `Raids` are not, so `deepnorth-sandbox` still gets
its `-modifier Raids None -modifier DeathPenalty Casual`. A disagreement is
printed in the generated header rather than silently dropped:

```
#   Resources: preset asks More, world pins MuchMore -- world wins
```

## `settings/overrides.yaml` — overrides, not copies

Each entry is one **key** in one **section** of one deployed config file, with
the currently-deployed value beside the value this tier wants. Sections are
mandatory: `ZenDragon.ZenRaids.cfg` has two different keys called
`Min Player Count`, so a section-less override is ambiguous.

A preset with no overrides gets an explicit empty list and a note. That is
deliberate — "the deployed value is already right for this tier" is a finding,
and an override table with nine identical rows is just a slower copy of the
config file.

The reasoning for every rule lives in `tier-policy.yaml` next to the rule, not
scattered across nine directories. Applying an override is an operator action;
`derive.py` never writes into a profile.

## `charactertemplate.yml` — the starting kit

ServerCharacters reads `CharacterTemplate.yml` from its own plugin directory,
watches it with a `FileSystemWatcher`, and ServerSyncs the text to clients. A
player creating a **new** character gets the skills, items and spawn point in it.
No RCON `give`, so nobody has to be online and nothing lands on the ground for
DropCleaner to eat after five minutes.

Schema, MEASURED by `PatchServerChars` from `PlayerTemplate.cs` / `ClientSide.cs`
at upstream `bb7d3cd6`:

```yaml
skills: {}    # map name -> float, applied with Skills.CheatRaiseSkill
items:  {}    # map prefab -> int, applied with Inventory.AddItem(name, n, 1, 0, 0, "", false)
spawn:  []    # list of {x, y, z} INTEGERS
```

Exactly those three top-level keys, and no others. The deserializer is built with
`IgnoreFields()` and the only `catch` is for `SerializationException`, which does
**not** catch YamlDotNet's `YamlException` — an unknown top-level key throws out
of a Harmony prefix. Comments are safe.

### Limitation an operator must know before promising a tier: quality is always 1

`Inventory.AddItem(name, count, 1, 0, 0, "", false)` — the `1` is the quality
argument and it is **hardcoded**. The format has no field for quality,
durability, variant, crafter or equip slot, and nothing is auto-equipped.

This is not a rounding error in the promise each preset makes. `pre-bonemass`
says "full iron kit"; 14 of its 20 kit entries are `quality: 3`, so what the
player actually receives is **unupgraded** iron — base damage, base armour —
sitting loose in the bag until someone walks it to a forge with the materials to
upgrade it. The same applies to every tier: the numbers below are how many kit
entries per preset arrive below the quality the preset specifies.

| Preset | kit entries at quality > 1 |
|---|---|
| `pre-eikthyr` | 9 |
| `pre-elder` | 12 |
| `pre-bonemass` | 14 |
| `pre-moder` | 15 |
| `pre-yagluth` | 13 |
| `pre-queen` | 20 |
| `pre-fader` | 23 |
| `pre-kall` | 24 |
| `deepnorth-sandbox` | 29 |

The upgrade materials are in the kit's `materials`, which means they are mostly
in `settings/chest-manifest.yaml` rather than the bag — so "arrive at a tier" in
practice means "arrive at a tier, next to a chest, with an upgrade session
ahead of you". Each template's header repeats its own count. There is no way to
fix this in the template; the only channels that can express quality are RCON
`give -quality Q` and an AdminQoL item set.

### Other consequences the generator handles

* **`items` is a map, and the preset's buckets are lists.** `pre-kall` and
  `deepnorth-sandbox` each name several prefabs in two buckets, so a naive
  conversion would silently drop one. Counts are summed, and the collisions are
  listed in the file.
* **The grid is finite and overflow is silent.** `Inventory.AddItem` returns
  `null` once full and ServerCharacters ignores the return. Measured against this
  world's 32 slots and the deployed `ItemStacksRewrite` stack table, the presets
  want 56 (`pre-eikthyr`) to 1248 (`deepnorth-sandbox`) slots. The generator
  therefore **partitions**: kit first, then chain items, then the cheapest
  materials, up to the slot ceiling — and everything else goes to
  `settings/chest-manifest.yaml`.
* **Level-0 skills are dropped.** `CheatRaiseSkill(name, 0)` is a no-op and every
  preset carries a full roster with the not-yet-relevant schools at 0. An
  unresolvable skill name is logged and skipped, not fatal, so modded skills
  (`Mining`, `Lumberjacking`, `Foraging`, `Blacksmithing`) are safe to list.
* **Only five skills move the gathering economy**, and three are custom skills
  registered by name rather than members of the vanilla enum (MEASURED by
  `YieldDesign`). Ore and stone need Smoothbrain `Mining` **and** vanilla
  `Pickaxes`; wood needs Smoothbrain `Lumberjacking` alone; berries need
  `Foraging` **and** `Farming`; crops need `Farming` alone; meat and hide are
  flat and skill-independent. All nine templates carry all five, except
  `pre-eikthyr`, which has `Mining` and `Pickaxes` at 0 on purpose: tier 1 has no
  pickaxe at all.

  Vanilla `WoodCutting` is **omitted from every template on purpose** and the
  omission is stated in each header so nobody adds it back. Smoothbrain
  Lumberjacking hard-patches `Skills.GetSkill(WoodCutting)` to a level-0 dummy
  and `IsSkillValid(WoodCutting)` to false, so it is permanently 0 and
  ImpactfulSkills' `WoodCuttingLootFactor = 3` is dead code. The drop list lives
  in `world.yaml` `skills.omit` with its reason, because inertness is a property
  of the deployed mod set, not of a tier.

#### Can the template reach the custom skills? Yes — measured, not assumed

This decides whether the skill half of every preset does anything at all, so it
was established **twice, independently**: from the IL (`monodis` over
`assembly_valheim.dll` and the deployed plugins) and from the live SkillManager
registries and Harmony patch chain on a booted server. The two agree.

* **Vanilla path.** `Skills::.cctor` sets
  `s_allSkills = Enum.GetValues(typeof(SkillType))` into an `initonly` static, and
  `CheatRaiseSkill` walks that array comparing `SkillType.ToString().ToLower()`
  to the name. Unaided it can therefore reach **only** members of the vanilla
  enum. It skips `SkillType` 0 and 999, the literal name `all` raises everything,
  and the write is `m_level += value` clamped to 0..100 — an **add**, which on a
  brand-new character is the same as a set but would **stack** if the template
  were ever applied twice. `Skills.GetSkill` creates the entry on demand through
  `GetSkillDef` (which SkillManager postfixes), so a never-used custom skill can
  go straight from absent to *n*.
* **Custom path.** Each Smoothbrain plugin ILRepacks its **own** copy of
  SkillManager, which Harmony-**prefixes** `Skills.CheatRaiseSkill` with
  `Patch_Skills_CheatRaiseskill`. The prefix walks its own registry, matches each
  skill's `internalSkillName` with `StringComparison.CurrentCultureIgnoreCase`
  (the IL operand is `ldc.i4.1`, which is `CurrentCultureIgnoreCase`, **not**
  Ordinal), raises it and returns `false` to consume the call; otherwise it
  returns `true` and the chain continues. Because each mod carries its own copy
  there are three independent prefixes, each matching only its own skill, so
  there is **no ordering hazard**. That is how `Mining`, `Foraging` and
  `Lumberjacking` work despite their `SkillType` being
  `(SkillType)englishName.GetStableHashCode()` — not enum members, so the prefix
  is the only possible route. Measured ids: `Mining` = 1408976878, `Foraging` =
  47719919, `Lumberjacking` = 1363793286.
* **The exact literal is `internalSkillName`**, which is
  `Regex.Replace(englishName, "[^a-zA-Z]", "_")`. The registered english names are
  literally `Mining`, `Foraging` and `Lumberjacking` — all pure alpha — so
  internal == display == what you type, and no mangling applies. Matching is
  case-insensitive; the templates use the registered casing anyway. A skill whose
  display name held a space or a digit would need the underscored form, which is
  why this is written down rather than assumed. `BlacksmithingExpanded` is a
  SkillManager skill too, so the same prefix applies; that its registered name is
  `Blacksmithing` is INFERRED, and it is not a yield driver so nothing economic
  rests on it.
* **It happens client-side.** The template is applied in
  `ServerCharacters.ClientSide.InitializePlayerFromTemplate.Postfix`, which calls
  `Player.m_localPlayer.GetSkills().CheatRaiseSkill(key, value, true)`. So the
  three Smoothbrain mods have to reach the **client** for the custom lines to
  land. They do — all four are `scope: shared` in the `ulfsland-dn` manifest,
  verified identical under ServerCharacters 1.4.16 and 1.4.17.
* **Precedence trap.** A matching prefix consumes the call, so a custom skill
  whose `internalSkillName` collides with a vanilla name captures it and the
  vanilla skill is never raised. This is history, not theory:
  `Smoothbrain-Farming` registered `Farming` and did exactly that until it was
  removed in tonight's 1.0 migration. Re-adding it would silently change what
  every template's `Farming:` line means.
* **`Farming` is resolved.** MEASURED from the `Skills/SkillType` enum in this
  build, vanilla `Farming` is `0x6a` = **106**, and there is **no id 15 at all** —
  so the "SkillType 106" once attributed to ImpactfulSkills *is* vanilla Farming
  under 1.0 numbering, and the "id 15" figure was pre-1.0.
  `ImpactfulSkills.dll` contains no reference to SkillManager, registers no custom
  skill, and reads `GetSkillLevel(0x6a)` — vanilla Farming. There is exactly one
  `Farming` and the templates reach it. From the same enum: `Pickaxes` = 12,
  `WoodCutting` = 13.
* **What is *not* reachable.** ImpactfulSkills neither uses SkillManager nor
  patches `CheatRaiseSkill`, so its own non-vanilla skills (`Hauling`, `Voyager`)
  cannot be set from a template at all. Neither drives yield, so no preset asks
  for them.

* **The spawn list has an off-by-one.** Selection is
  `Random.Range(0, spawn.Count - 1)`, whose upper bound is exclusive, so with N
  entries only indices `0..N-2` are ever chosen. `spawn.yaml` lists real points
  only; the generator duplicates the last one.

**One server holds one template.** There is no per-character, per-tier or default
section. Switching preset means replacing the file.

### The `spawn:` block — the one coordinate, and why it is measured

Everything else in a template comes out of YAML. A spawn cannot: a coordinate is
only usable if the ground under it is dry, and no amount of YAML knows that.

```
derive.py spawn <World>    probe terrain, choose, write <preset>/spawn.yaml
derive.py build <World>    render the template from spawn.yaml
derive.py check <World>    re-check spawn.yaml against the current placements
```

`spawn` boots the dedicated server in an rsync'd sandbox (own port, own savedir,
nothing live) and samples Valheim's own `WorldGenerator` at **1 m with full
pregeneration** through `blueprints/run_patchscan.sh`. A point is accepted only
if it is:

* **on land with freeboard** — `SPAWN_FREEBOARD_M` = 2 m above the water plane at
  the exact integer that gets written, plus 0.5 m across a 4 m disc so it cannot
  be a pinnacle in a bog;
* **at the base** — 6 to 120 m outside the blueprint's footprint *rotated by the
  placement's yaw*, so nobody wakes up inside a wall;
* **joined to it on foot** — a metre-by-metre walk to the nearest point on that
  footprint that never drops below 0.5 m of freeboard and never steps more than
  1.5 m, which is what rules out a channel or a ravine between spawn and base.

No provable point means `spawn: []`, the vanilla spawn, and a recorded refusal
carrying the numbers. A missing spawn is a visible gap; a wet one reaches the
player.

Two numbers are load-bearing and were both wrong before:

* **Sea level is y = 30**, not 0 — see `derive.SEA_LEVEL_M` for three independent
  measurements. `site_finder.WATER_LEVEL` read the ocean-floor clamp (~4) as the
  surface, a 30 m error that let sites and spawns sit under water while passing.
* **The 8 m seedscan grid cannot answer this.** `run_scan.sh` leaves
  pregeneration off, so its heights are river-free. At the spawn that put a
  character in the sea it reports 30.17; the true river-aware height is 26.74.

The candidates *are* lattice points (step 1, integer half, half-integer centre),
so the verdict is taken at the coordinate that ships rather than half a cell from
it, and `y` is `ceil(terrain + 1)` — rounded up, never down.

### The manual fallback, if a template ever has to be bypassed

Nothing about the fallback is new and none of it is duplicated here. Per preset:

| Part | Fallback | Where |
|---|---|---|
| Global keys | RCON `addGlobalKey`, one at a time with read-back | `jumpstart.py apply <preset> --keys-only --commit`; the key list is in `keys.yaml` |
| Gear and materials | RCON `give`, ledger-deduplicated — needs the player **online**, drops on the ground, DropCleaner eats uncollected non-magic drops after 5 minutes | `jumpstart.py apply <preset> --players <id> --items-only --commit` |
| Skills | **No server-side path.** AdminQoL `itemset` applies to the invoking admin's own local character only | `jumpstart.py itemset <preset>`, then the exact hand steps printed by `ManualSkillBackend` |
| Station levels | An admin places the extension pieces, from the **`ulfsland-admin`** edition only | `stations` in `presets/<preset>.yaml`; `jumpstart.py show` prints them |
| World modifiers | Paste into `valheim.env` `SERVER_ARGS` and restart | `settings/world-modifiers.env` |
| Config overrides | Operator edits the named key in the named section | `settings/overrides.yaml` |
| Bulk materials | RCON container stocking, no player online | `settings/chest-manifest.yaml` |

## `settings/chest-manifest.yaml`

The overflow the template cannot carry, as `prefab -> count`, with its measured
slot cost and the number of chests it implies.

It is stocked **headlessly**, which is what makes the partition acceptable rather
than a loss (MEASURED by `BlueprintHunt` from `ValheimRcon`):

```
findObjects -prefab piece_chest -near <x> <y> <z> <r>     # -> ZDO ids
addItemToContainer <id:userid> <item_name> -count <n>     # -> stock each chest
```

Chest inventories are separate grids, so none of the 32-slot truncation applies.
Nobody needs to be online. Two caveats: RCON responses hard-truncate at 4050
payload bytes and `findObjects` has no pagination, so keep the radius tight; and
RCON `spawn` cannot set object data, so a chest cannot be pre-filled at spawn
time. If the operator ever hand-builds and saves a stocked base from the
`ulfsland-admin` seat, Infinity Hammer's `hammer_save data=true` captures chest
contents into the blueprint and the manifest becomes unnecessary for that preset.

When `placements.yaml` reports a `containers:` block, the manifest compares its
overflow against the placed capacity and records a `capacity_shortfall_slots`
rather than guessing — that is `BlueprintHunt`'s signal to add a storage
blueprint.

## Commands

```
derive.py list                                  worlds, presets, and who owns what
derive.py build Ulfsland [--preset NAME ...]    write the tree
derive.py check Ulfsland [--preset NAME ...]    re-derive and diff; never writes
derive.py spawn Ulfsland [--preset NAME ...]    probe terrain, rewrite spawn.yaml
                          [--check]             ... or re-probe and diff only
```

`spawn` needs a server install (`--vh-src`, or `VH_SRC`) because it samples the
game's own generator; `list`, `build` and `check` need nothing but Python and this
tree. `build` also creates each `blueprints/` directory so the layout is complete.
It never writes into `blueprints/` or `placements.yaml`, and never deletes
anything.
